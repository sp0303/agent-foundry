1. Verdict on your raw plan

The shape is right. Six changes make it survive contact with reality.

Your plan is essentially a software company expressed as agents, which is the most-studied multi-agent pattern there is. MetaGPT (product manager, architect, project manager, engineer run by written SOPs) and ChatDev (CEO, CTO, programmer, tester) both proved it works for small projects. The same research also shows where it breaks: a Berkeley study of seven multi-agent frameworks found that most failures come from unclear specs, agents drifting out of their roles, and weak verification, not from the models being too dumb. So the changes below are all about contracts, verification and separation of duties.

Add a role

Separate QA / reviewer agent

If the architect writes the tasks, answers the questions and also judges the merge, it grades its own homework. Give review to an independent agent, ideally on a different vendor than the dev who wrote the code.

Change a rule

CI is the judge, not the architect

“Runs test cases” should mean a pipeline with required checks. The architect reads the results and decides; it never merges on its own opinion that tests pass.

Add a gate

Human approves the plan, not just the result

Put one approval after the architect’s scope and before any code. Catching a wrong scope costs one message; catching it after deployment costs the whole run.

Change a rule

Questions travel as structured requests

Devs don’t chat freely. A blocked dev returns a formal question (A2A’s “input required” state) to the architect, who answers or escalates to the BA and then you.

Change a rule

Parallelise only independent modules

Coding has fewer truly parallel pieces than research. The architect should cut work along interfaces (API contracts first) so parallel branches don’t collide at merge.

Add a component

A tool registry, so tools build on tools

Your goal is agents that build tools. Every finished tool gets published as an MCP server with a card describing it, so the next project’s agents can reuse it instead of rebuilding.

2. System topology

Who talks to whom

A hub-and-spoke: the architect is the hub for all engineering traffic, the BA is the only agent that ever talks to you. Agents talk to each other over A2A; agents reach tools, repos and pipelines over MCP. Colour marks the vendor each seat could run on.

One session or two for BA and architect?

You described the main agent as “BA + architect”. I’d keep them as two agents behind one chat. The BA’s context stays full of your language, your users and your priorities; the architect’s context stays full of code, interfaces and constraints. Mixing them means every design decision pays the token cost of the whole requirements conversation, and the BA loses its ability to challenge the architect on your behalf. You still only ever talk to one session.

3. Lifecycle

From raw idea to verified tool, in ten steps

Each lane is a seat, each box is a step in order. The two red diamonds are the only moments the system waits for you.

  1. Raw idea. Voice note, paragraph, screenshot, whatever you have.
  2. Discovery. The BA asks at most a handful of sharp questions, then writes a PRD: problem, users, user stories, acceptance criteria in Given/When/Then form, non-goals, and success metrics.
  3. Scope and design. The architect turns the PRD into architecture decision records, a component view, interface contracts, a task graph with dependencies, and a risk list.
  4. Plan approval. The BA translates the architect’s plan back into plain language for you. You approve, trim or redirect. Nothing is built before this.
  5. Build. Each dev gets one task contract, works in its own branch or worktree, writes tests with the code, and opens a PR. Questions go back to the architect as structured requests.
  6. Review. The QA agent reviews the diff against the task’s acceptance criteria and adds missing tests. CI runs lint, unit, integration, security scan and licence checks.
  7. Merge. The architect merges only green PRs, in dependency order, then runs the integration and end-to-end suite on main.
  8. Staging deploy. DevOps ships to a staging environment through the pipeline, runs smoke tests, and returns a URL plus a rollback command.
  9. Report. The BA checks the result against each acceptance criterion and sends you a short report: what works, what doesn’t, what it cost.
  10. Verify. You try it. Feedback becomes new stories and the loop restarts at step 2 or 3. Approval triggers the production deploy and publishes the tool to the registry.
4. Roles and responsibilities

Every seat, with its authority written down

Role drift is one of the most common multi-agent failure modes, so each seat gets a charter: what it owns, what it decides, what it must never do, and what it hands over. These become each agent’s system prompt and its A2A Agent Card.

Persona: principal architect, 20 years across distributed systems, security and delivery. Reports to BA. Directs devs, QA, DevOps.

Owns

  • Scope boundary: what is in, what is out, what is deferred.
  • Architecture decision records for every non-trivial choice (context, options, decision, consequences).
  • Component and container views in the C4 style, plus data model.
  • Interface contracts first: OpenAPI, JSON Schema or MCP tool schemas, written before devs start.
  • The task graph: decomposition, dependencies, which tasks can run in parallel.
  • Definition of Ready and Definition of Done per task.
  • The repository’s AGENTS.md: coding standards, commands, conventions every dev agent reads.

Decides

  • Tech stack, patterns, library choices, build vs reuse (checks the tool registry first).
  • Which model and vendor each task goes to, within the budget.
  • Merge order and whether a green PR is actually acceptable.
  • Release go / no-go for staging.

Standards it must check against

  • Quality attributes from ISO/IEC 25010: reliability, security, maintainability, performance, portability.
  • Security: OWASP Top 10 and ASVS level chosen per project, threat model (STRIDE) for anything exposed.
  • Twelve-factor app for services; config in environment, never secrets in code.
  • Semantic versioning, Conventional Commits, protected main, PR-only merges.
  • Test pyramid with coverage floor; contract tests on every interface.
  • Supply chain: SBOM, dependency and licence scan, pinned versions, SLSA-style provenance.
  • Observability: structured logs, metrics, traces from day one.
  • Delivery health measured with DORA metrics.

Must never

  • Write feature code itself (it loses the reviewer’s distance).
  • Merge on red CI or skip a required check.
  • Change scope without going back through the BA.

Persona: senior business analyst, 20 years. The only agent you talk to. Represents you inside the system.

Owns

  • Turning a raw idea into a PRD: problem statement, personas, user stories, acceptance criteria, non-goals, success metrics.
  • A glossary so every agent uses the same words for the same things.
  • Prioritisation (MoSCoW or similar) and the backlog of your feedback.
  • Translating the architect’s plan and reports into plain language.
  • Final acceptance check against the criteria before anything comes to you.

Decides

  • When requirements are clear enough to hand to the architect (Definition of Ready).
  • Which dev questions can be answered from the PRD and which must come to you.

Must never

  • Make technical design decisions.
  • Tell you something is done that the architect hasn’t verified.
  • Ask you more than a few questions at once.

Persona: senior engineer, one task at a time. Can run on any vendor.

Owns

  • Implementation of exactly one task contract, in its own branch or git worktree.
  • Unit tests and any contract tests for the interfaces it touches.
  • A PR with a summary, linked task ID, test evidence, and any assumptions it made.

Must never

  • Edit files outside the task’s declared paths, or change an interface contract.
  • Guess on ambiguity; it raises a structured question and pauses instead.
  • Push to main or touch deployment config.

Persona: staff QA and security reviewer. Deliberately on a different vendor than the author of each PR.

Owns

  • Review of each PR against its acceptance criteria, not just “does it compile”.
  • Test design: edge cases, negative paths, end-to-end scenarios from the user stories.
  • Reading CI results, security scan findings and coverage deltas.

Decides

  • Approve or request changes. Its approval is a required check.

Must never

  • Fix the code itself. Fixes go back to the dev so the author learns and the history stays clear.

Persona: platform engineer. Operates through pipelines, never by hand.

Owns

  • CI/CD pipelines, infrastructure as code, environment configuration.
  • Staging and production deploys, smoke tests, rollback.
  • Secrets handling through a secrets manager; agents never see raw credentials.
  • Publishing finished tools to the registry as MCP servers.

Must never

  • Deploy to production without your recorded approval.
  • Run ad-hoc commands against production; everything goes through the pipeline so it is logged and repeatable.
5. Branching, merge and release

How parallel branches come back together safely

Git is the shared memory between vendors. Claude, Gemini and Codex agents can’t read each other’s context windows, but they can all read the same repository, the same ADRs and the same AGENTS.md. That makes the repo, not the chat, the source of truth for the whole firm.

6. Model routing

Your insight is right: expensive brains plan, cheaper hands build

This split has a research basis. The “LLMs as tool makers” work had a strong model write reusable tools once and a lightweight model apply them, and matched the strong model’s accuracy at much lower cost. Anthropic’s own research system uses a heavier lead agent directing lighter subagents. A couple of your model names need updating to the current lineup, so here is the mapping I’d use today.

SeatPrimaryCross-vendor alternativeWhy this tier
Business analystClaude Opus 5.5 high effortGPT-6 AstraAmbiguity and judgement about people. Low token volume, so the premium price barely matters.
ArchitectClaude Opus 5.5 max effort; Fable 5.1 for the hardest designsGemini 3 Deep Think as a design second opinionEvery downstream token depends on its decisions. The place to spend the most per call.
Developer, complex taskClaude Sonnet 5GPT-6 Astra via Codex; Gemini 3.x via AntigravityStrong coding at a mid price. Mix vendors across tasks to get diverse strengths.
Developer, routine taskClaude Haiku 4.5Gemini 3.x Flash; GPT-5.6 SolBoilerplate, docs, test scaffolding, migrations with a clear pattern.
QA / reviewerAny vendor that did not write the PRRotateCross-vendor review catches blind spots a model shares with itself.
DevOpsClaude Sonnet 5 or Haiku 4.5Gemini 3.x FlashThe risk here is permissions, not intelligence. Deterministic pipelines do the actual deploy.

Keep the model as configuration, never hard-coded. Vendors ship and retire models every few months; for example OpenAI is retiring GPT-5.5 from ChatGPT and Codex in October 2026. A routing table you can edit in one file will outlive any specific pick. And budget for it: multi-agent runs used roughly fifteen times the tokens of a normal chat in Anthropic’s measurements, so put a hard token budget on every task.

7. Cross-platform communication

How a Claude agent, a Gemini agent and a Codex agent work as one team

Two open protocols now do most of the work, and both sit under the Linux Foundation’s Agentic AI Foundation. A2A is agent-to-agent: each agent publishes an Agent Card describing its skills, and work moves as tasks with a fixed lifecycle (submitted, working, input required, completed, failed, and so on). MCP is agent-to-tool: how an agent reaches Git, CI, databases, or a tool you built last month. The rule of thumb: A2A routes the task to the right specialist, MCP gives that specialist its tools.

Conversationyou ⇄ BA
A single chat. Could be Claude.ai, a Slack bot, or your own web UI over AG-UI.
Coordinationagent ⇄ agent
A2A tasks between BA, architect, devs, QA and DevOps. The “input required” state is exactly your dev-asks-architect loop. Signed Agent Cards arrived in A2A 1.0 for verifying who you’re talking to.
Instructionsportable across vendors
AGENTS.md for repo rules and SKILL.md files for reusable procedures. Claude Code, Codex and Antigravity all read these formats, so one set of standards governs every vendor.
Toolsagent ⇄ system
MCP servers for Git, CI, issue tracker, cloud, secrets proxy, and every tool the foundry has built before.
Shared statetruth
The Git repo (code, ADRs, PRD, task files) plus an artifact store for builds and reports.
Observabilitycost and audit
OpenTelemetry traces with one trace ID per user request, token cost per agent, and a full log of decisions for replay.

What a task contract looks like on the wire

The single biggest lever, according to Anthropic’s research-system write-up, is how precisely the lead agent delegates: a clear objective, output format, tools and boundaries. Here is the payload the architect sends a dev inside an A2A message:

{
  "task_id": "T-014",
  "title": "Rate-limit middleware for /v1/convert",
  "objective": "Reject >60 req/min per API key with HTTP 429",
  "context_refs": ["docs/adr/0007-rate-limiting.md", "api/openapi.yaml#/paths/~1v1~1convert"],
  "allowed_paths": ["src/middleware/**", "tests/middleware/**"],
  "interfaces_frozen": ["api/openapi.yaml"],
  "acceptance": [
    "Given 61 requests in 60s with one key, the 61st returns 429 with Retry-After",
    "Given two keys, limits are independent"
  ],
  "definition_of_done": ["unit tests pass", "coverage >= 85% on changed files", "no new high SAST findings"],
  "branch": "feat/T-014-rate-limit",
  "budget": { "max_tokens": 400000, "max_minutes": 45 },
  "assignee": { "vendor": "openai", "harness": "codex", "model": "from-routing-table" },
  "escalation": "ask architect via input-required; do not guess"
}

9. Failure modes and guards

Where teams like this break, and what stops it

FailureWhat it looks likeGuard in this design
Vague specDevs build something plausible but wrong.PRD with testable acceptance criteria; task contracts with frozen interfaces; plan approval by you.
Role driftArchitect starts coding, dev redesigns the API.Written charters; path allow-lists enforced by the harness, not just the prompt.
Silent assumptionsDev guesses instead of asking.“Ask, don’t guess” rule; assumptions must be listed in every PR.
Rubber-stamp verificationReviewer confirms it compiles, not that it meets the goal.Independent cross-vendor QA; CI as a required check; BA re-checks against acceptance criteria.
Merge collisionsParallel branches conflict at the end.Contracts first, tasks cut along interfaces, merge in dependency order.
Runaway cost or loopsAgents keep revising forever.Per-task token and time budgets; max review rounds; escalation to the architect then you.
Prompt injection via toolsA web page or dependency tells an agent to leak secrets.Secrets only via a proxy; outbound network allow-lists; tool output treated as data, never instructions.
Unsafe deployAgent pushes broken code to production.Pipeline-only deploys, staging first, human approval for prod, one-command rollback.
10. Build plan

A phased way to get there

  1. Single-vendor walking skeleton (1–2 weeks). Claude Code only: BA and architect as custom agents, two dev teammates in worktrees, GitHub Actions as CI. Build one small real tool end to end. Measure tokens, time and how often you had to intervene.
  2. Contracts and charters (week 3). Freeze the PRD template, ADR template, task-contract JSON and the five role charters from section 4. Add the plan-approval gate and the QA agent.
  3. Second vendor (weeks 4–5). Add Codex as a dev and as the reviewer of Claude-written PRs, first via CLI workers, then behind a small A2A adapter. Compare quality and cost per task.
  4. Third vendor and DevOps (weeks 6–7). Add a Gemini/Antigravity seat, the DevOps agent with staging deploys, and the trace and cost dashboard.
  5. Tool registry (week 8 onward). Every approved tool is published as an MCP server with a card. The architect must search the registry before designing anything new. This is where the foundry starts compounding.
11. Open questions for our next round

Things to decide together

What kind of tools? Internal CLIs, MCP servers, web apps and data pipelines need very different DevOps seats and test strategies. Pinning the first category down will shape everything else.

Where does it run? Your laptop, a single cloud VM, or each vendor’s hosted sandbox. This decides between approaches A, B and C above.

How much autonomy between checkpoints? Two human gates is my default. Some teams add a third after the first merge on main.

Budget per tool. A ceiling in dollars or tokens per project lets the architect trade model tiers against each other instead of always picking the most expensive.

Should agents improve their own charters? After each project, a retrospective agent could propose edits to AGENTS.md and the role prompts, with you approving. Powerful, but it needs careful review.
